# 项目三：培养方案学分自助核查工具 —— 设计方案

日期：2026-08-29

## 背景与目标演进

最初定位（简历/面试项目）：一个命令行工具，输入自己的培养方案 + 成绩单，输出学分核算报告，验证对象只是刘拾玉本人的化学（强基计划）数据。

对话中目标扩大为：**面向全校学生的公益免费查询网页**，长期规划是一个 multi-agent 数据平台（内置培养方案库 + 培养方案自动爬取/解析 + 学生自提交培养方案 + 通识课表知识库 + 选课推荐）。

这个平台目标一次性设计会失焦，且后面几块都依赖核算逻辑本身先跑通，所以拆成 5 个子项目，本轮只完整设计并落地其中的子项目 1+2。

## 子项目拆分

## 子项目 3 的已确定决策（供后续设计沿用）

- **自提交的培养方案数据不自动合并进内置数据库**：学生自提交的方案只服务提交者本人的核算，不经审核就永久保留，避免"别人乱填坑他人核算结果"的风险。是否人工审核后收录为内置数据，留到子项目 3 正式设计时再定。

## 本轮设计：子项目 1 + 2

### 架构总览

不做通用 PDF 自动解析（第一版跳过 pdfplumber/pymupdf 之类的方案）。培养方案已经由人工读取 PDF 后手写为结构化 JSON（见 `data/plan_chem_qiangji_2022.json`），作为权威数据源。核心链路：

```
教务系统页面（学生已登录）
   └─ 学生框选”已修课程”表格，复制
        └─ 粘贴到静态网页的文本框
             └─ 网页 JS 端：容错解析文本 → 匹配课程 + 规则引擎求值
                  └─ 展示学分核算报告（纯前端，无后端，不存数据）
```

全程没有后端服务器，不经手任何账号密码，不存储任何学生数据——这是刻意的隐私设计，而不是偷懒：一旦引入后端存储，就要对全校同学的学籍数据负安全责任，成本和风险都远高于当前的"纯前端一次性计算"模式。

### 数据结构（plan.json）

已按此 schema 写好 `data/plan_chem_qiangji_2022.json`，从 PDF 原文逐字段转录，各类别学分合计已核对与原文一致（30+24+32.5+16.5+20+8+9=140）。

```json
{
  "plan_id": "chem_qiangji_2022",
  "categories": [
    {
      "name": "个性培养",
      "required_credits": 20,
      "open_pool": false,
      "courses": [
        {"code": "CH10044", "name": "科学研究训练实践", "credits": 3, "group": "特色课程", "mandatory": true},
        {"code": "CH06062", "name": "化学前沿", "credits": 2, "group": "模块1"}
      ],
      "rules": [
        {"type": "min_credits_in_group", "group": "特色课程", "min": 9},
        {"type": "min_credits_in_groups", "groups": ["模块1","模块2","模块3","模块4","模块5"], "min": 6},
        {"type": "remainder_open", "note": "满足以上两条后，剩余学分可来自模块1-5超出部分或跨院系选课"}
      ]
    }
  ]
}
```

规则引擎只实现三种类型，不做通用表达式引擎（YAGNI）——这份培养方案里遇到的特殊规则都能归到这三种：

- `min_credits_in_group`：某个课程组至少修满 N 学分
- `min_credits_in_groups`：多个课程组合计至少修满 N 学分（可跨组）
- `remainder_open`：说明性规则，标记"其余学分可从更大范围课程/跨院系选课中获得"，不参与硬性校验，只在报告里提示

`通识选修`类别标记 `open_pool: true`——原文本身不枚举具体课程（按学校通识选修课修读办法执行），核算时这个类别只按成绩单里学生自己标注的类别名匹配，不去比对课程编号。

### 匹配模块（成绩单 ↔ plan.json）

以课程编号为准匹配，不信任成绩单/教务系统自带的类别标签：

- plan.json 里能查到编号 → 按 plan 的归类计入对应类别/分组
- 编号不在 plan.json 里（通识选修池、跨院系选修）→ 归入"未识别/待确认"，不臆测归类
- 编号在 plan.json 里，但成绩单自带的类别标签与 plan 归类冲突 → 报告里显式警告，不静默二选一

这条设计对应对话里提到的真实案例："计算化学"和"科学研究训练实践"的分类可能与学生自己以为的归类不一致，工具要把冲突亮出来而不是替学生瞎猜。

### 数据录入方式（v1：手动复制粘贴，不依赖书签脚本）

规划阶段发现更简单可靠的路径：不用等书签脚本抓 DOM（需要真实页面结构才能写选择器），直接让学生在教务系统"已修课程"页面框选表格、复制，粘贴进网页的文本框。浏览器复制表格时通常会带 Tab 或连续空格分隔，前端写一个容错解析器（按 Tab / 多空格 / 逗号分列，用正则识别课程编号列和学分列）就能处理，不需要知道真实 DOM 结构。这样原设计里"缺页面 HTML 才能写抓取代码"的阻塞项直接解除。

书签脚本自动抓取+自动复制到剪贴板，作为**后续增强**（免去手动复制这一步），不在 v1 范围内，需要拿到真实页面结构后再做。

### 前端页面（静态站点，GitHub Pages 托管）

- 首页：内置培养方案选择（v1 只有"化学（强基计划）2022版"一项）+ 书签脚本安装引导
- 粘贴框：学生把书签脚本复制的 JSON 粘贴进来
- 结果页：
  - 类别对比表：类别 | 要求学分 | 已修学分 | 缺口
  - 个性培养细项：特色课程达标情况、模块1-5达标情况、剩余可自由学分
  - 未识别课程列表（含警告：与 plan 归类冲突的课程）
- 纯静态 HTML/JS，无后端，不做任何数据落盘或上传

### 测试

没有历史"标准答案"可比对（此前对话中提到的手动核对结论产生于另一次会话，本次会话拿不到）。等拿到真实"已修课程"数据后，会挑 1-2 个类别现场手算一遍做交叉验证，不假设已有基准。另外用构造的边界用例覆盖规则引擎：刚好卡在 9/6 学分边界、跨模块组合刚好凑够 6 学分等情况。
